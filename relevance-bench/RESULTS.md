## Findings

<!-- findings:begin (hand-written; preserved across re-runs) -->
Measured on develop `3790ba95` plus this branch (`atlas v0.1.52-700-g1a75deae`). The baseline was first frozen on `7f7e7b07`;
"before/after" below compares the two. Since then develop gained #135 (deterministic search tie order) and #156
(bodies of large functions surfaced with `body_elision`, and a citations-first code_query trimmer). The numbers are from the tables above. Each
finding has a repro on the frozen corpora, where `$C` is the corpus checkout that
`relevance_bench.py` materializes (`<work>/corpora/<corpus>`) and `$DB` is
`sqlite://<work>/stores/<corpus>/atlas.db`, indexed with `atlas --db $DB index $C`. No ranking code changed in this
benchmark PR. Every finding below is proposed as its own follow-up ticket, and each fix should ratchet `GATE.json`.

**What holds up.** Bare-identifier lookup works: the `search_exact` control puts the entity first in 71 of 76 cases
(0.934). `code_query` routes `what calls <E>?` well: entity-first is 0.921 and query-word pollution is 0.013. Every
definition is somewhere in the top 10 for 73 of 76 questions (R@10 0.961). On the clean, single-vocabulary C corpus,
definition MRR is 0.97–1.00 on every surface. The trouble is in natural-language phrasing, mixed vocabularies and
generic words, which is what the ticket reported.

### F1 — Question-template words are ranked as search terms (stopword pollution)

137 of 540 named-question surface results (57 distinct questions) put a symbol at rank 1 that matches only a word
of the phrasing ("where", "is", "calls", "exception"), and it is not a labelled hit. The worst offenders are:
`where`, a key at `requests/pyproject.toml:84`
(rank 1 for 21–22 of the 38 mixed-corpus `where is <E> defined?` questions on every surface, and in search's top 10 for all 38);
`num_401_calls`, a field at `requests/src/requests/auth.py:134` (rank 1 for 22 of 38 `what calls <E>?` questions on search and context);
`is`, a field at `packages/runtime-dom/src/jsx.ts:343`; and `calls`, a field at `packages/compiler-sfc/src/script/resolveType.ts:142`.

- mixed “where is Valid defined?” [search, context, code_query] → `where` requests/pyproject.toml:84; `is_valid` leveldb/util/env_windows.cc:94; `Valid` leveldb/db/skiplist.h:68
- ts-vue “where is ref defined?” [all three] → `is` packages/runtime-dom/src/jsx.ts:343; `isRef` packages/shared/src/toDisplayString.ts:16; `isRef` packages/reactivity/src/ref.ts:48. `ref` itself (ref.ts:59/62/64) is not in the top 10 on any surface (MRR 0).
- Repro: `atlas --db $DB --repo $C search 'where is Valid defined?' --json` (mixed-cpp-python).
- Likely cause, unverified: `internal/engine/searchguard.go:152` `searchStopwords` lists where/what/how/… and is consulted
  by the off-topic guard, the code_query relevance floor and passage extraction. Nothing under `internal/lexical`
  handles stopwords, though, so the BM25 query keeps every token. `is`, `calls` and `defined` are in no list.
- **Proposed ticket:** "Lexical retrieval: drop question-template words from the BM25 query when the question also names an
  identifier." Acceptance: query-word top-1 ≤ 0.05 for definition and callers on all three surfaces.

### F2 — Entity-first routing exists for "what calls", not for "where is … defined"

Definition entity-first is 0.618 on search and 0.632 on context and code_query (0.645 on `7f7e7b07`; one
tie, "where is unref defined?", now resolves to `unref1` from a d.ts test). The bare-name control on the same
entities scores 0.934. Twenty-four definition questions rank the entity first by bare name but not as a question.
For 25–26 the definition is in the top 10 but not first. code_query anchors the entity for callers questions
(0.921) but not for definition questions (0.645).

- mixed “where is Log defined?” → the free function `Log` (leveldb/util/env.cc:41) is not in the top 10 on any surface (MRR 0).
- mixed “Open error exception handling” and “Append error exception handling” [all three] → the top 5 are Python
  classes `RequestException`, `ConnectionError`, `HTTPError`, `RetryError`, `InvalidJSONError` (requests/src/requests/exceptions.py).
  The C++ entities `DB::Open` (leveldb/db/db_impl.cc:1503) and `PosixWritableFile::Append` (leveldb/util/env_posix.cc:293)
  are not in the top 10 (MRR 0). A generic entity name plus generic error words produces cross-language noise.
- ts-vue “computed error exception handling” → `callWithErrorHandling`, `callWithAsyncErrorHandling` and `ErrorHandlingOptions`
  rank above `computed`. The labelled `ComputedRefImpl` readonly warning (packages/reactivity/src/computed.ts:147-153) is never reached.
- Repro: `atlas --db $DB --repo $C search 'where is Log defined?' --json` vs `atlas … search Log --json`.
- **Proposed ticket:** "Entity-first routing for where-defined and entity-scoped questions: a question token that is an
  exact indexed symbol name anchors that symbol at rank 1, as code_query already does for 'what calls'." Acceptance:
  definition entity-first ≥ the search_exact control on all surfaces, and error_handling MRR > 0 for Open/Append.

### F3 — A case-exact whole-name match does not outrank case-folded or partial matches

The bare-name control misses 5 of 76:

- **Proposed ticket:** "search: a case-exact whole-name symbol match ranks above case-folded and identifier-piece matches."

### F4 — Non-code facts outrank code for code-shaped questions

66 named-question surface results have a config or workflow fact at rank 1: the `where` key (65) and the `trigger` key in
`.github/workflows/ecosystem-ci-trigger.yml:13` (code_query, “what calls trigger?”). For the bare `json` lookup, the
Makefile target `json` (requests/docs/Makefile:79) and TypedDict fields outrank the method `Response.json` (models.py:1091, rank 5).
`--corpus code` does not help: `atlas search 'where is Valid defined?' --corpus code` still ranks the pyproject key first.
- **Proposed ticket:** "Config keys, workflow YAML and Makefile targets rank below code symbols for code-shaped questions,
  and `--corpus code` excludes file-level config facts." Acceptance: non-code@10 = 0 on definition and callers questions.

### F5 — search refuses real identifiers inside a question (false off-topic)

On ts-vue, `atlas search "what calls warn?"` returns `results: []` with `degraded_reason: query_has_no_code_identifier_tokens`.
The same happens for `ref`, `reactive`, `track` and `trigger`: 5 of 19 vue callers questions, which is the 0.066 empty rate in
the callers table. Each of those names is an indexed function, and `atlas search warn` returns 5 hits. camelCase
(`toRaw`) and capitalised C++ names pass the guard.
- Repro: `atlas --db $DB --repo $C search 'what calls warn?' --json` (ts-vue).
- Likely cause: in `queryHasCodeIdentifierTokens` (internal/engine/searchguard.go), a lowercase plain-word identifier in a
  multi-word query qualifies only through a vouching hit on the returned page. These questions' pages have none.
- **Proposed ticket:** "Off-topic guard: a query token that is an exact indexed symbol name qualifies the query as code."
  Acceptance: search callers empty rate 0.

### F6 — code_query's relevance floor (#60) grounds on generic words that happen to be symbol names, and keeps citations retrieved only by stopwords

code_query refuses 16 of 36 adversarial questions (0.444), grounds 3, and answers 17 with confident noise:
- mixed “how does this code work” → `code` leveldb/include/leveldb/status.h:88. The verdict is `grounded_by: exact_name`, with
  `ignored_terms: [code, work]`.
- mixed “what calls the function?” → `function` leveldb/util/env_windows.cc:689 and `function` leveldb/util/env_posix.cc:764,
  methods literally named `function` (`grounded_by: exact_name`).
  On ts-vue the same question returns `calls` packages/compiler-sfc/src/script/resolveType.ts:142.
- ts-vue “what is the purpose of the module” → `module` packages/compiler-sfc/src/parse.ts:69 (`grounded_by: exact_name`).
  On cJSON, which has no symbol named `module`, the same question is correctly refused.
- Rule 3 of the floor ("no discriminative term and a cited symbol is named exactly what it typed",
  docs/reference/mcp/README.md) fires on words the floor itself lists as generic.
- A second defect: “where is Valid defined?” returns `ok`, and its citation #1 is the `where` key (`relation: lexical`),
  although `query_terms` is `[valid, defined]`. The prune step demotes citations that matched only generic words, but not
  citations that matched no query term at all.
- Repro: MCP `code_query {question: "how does this code work", require_citations: true}` on mixed-cpp-python.
- **Proposed tickets:** (a) "relevance floor: the exact_name rule ignores generic and stop words". (b) "relevance floor:
  prune lexical citations that match no query term". Acceptance: code_query adversarial safe ≥ 0.9.

### F7 — `context` never refuses and always ships a ~30 KB bundle

context refuses 0 of 36 adversarial questions, unchanged by the rebase. For “the of and to in is it for that with” it returns 17–32 symbols (27–31 KB),
led on cJSON by the `with` key in `.github/workflows/ci-fuzz.yml` and Unity fixtures. On named questions context sets
`truncated: true` 100% of the time and code_query 0% of the time, both unchanged. Mean serialized cost per answer,
`7f7e7b07` → now:

| surface | definition | callers | error_handling |
|---|---:|---:|---:|
| search | 2.7 → 2.7 KB | 2.3 → 2.3 KB | 3.1 → 3.1 KB |
| context | 31.1 → 31.4 KB | 30.7 → 30.6 KB | 32.0 → 32.2 KB |
| code_query | 32.4 → 32.3 KB | 30.1 → 29.8 KB | 33.5 → 33.0 KB |

#156 changed what is inside the bundles: 36 of the 76 cJSON and mixed-corpus definition and error_handling answers now carry

At roughly 4 bytes per token, code_query and context still cost about 8k tokens for a single-definition lookup.
- **Proposed ticket:** "context: apply the code_query relevance floor (an `insufficient` / below-floor status) and size the
  bundle to the question's specificity." Acceptance: context adversarial safe ≥ 0.9, and definition-question bytes ≤ 8 KB.

### F8 — Tied results ordered by store insertion order — FIXED on develop by #135 (kept as a regression control)

first in one run and leveldb/db/db_test.cc:321 in the other.

On `3790ba95` (#135: total order score, path, line, name, …):
- 16 of 724 lists still differ between two fresh stores. None differ at rank 1, and no metric of any query changed:
  the gated drift is **0** over all 159 thresholds.
- All 16 are in `atlas search` (including the bare-name control), below rank 1. context and code_query lists are now identical across stores.
- What is left is not an exact tie. The scores differ in the last ULP, and which document gets the larger rounding depends on the

- Within one store a repeated query is identical.
- The gate keeps one query of slack per set (README.md) and holds this as a control: a tie-order regression shows up as drift between two runs.

### F9 — Graph packing puts test callers ahead of the error types a question names

error_handling R@10 is 0.592 on search but 0.527 on context and code_query, and test@10 is 0.133 vs 0.250.
- mixed “rewind_body error exception handling”: search → `rewind_body`, `UnrewindableBodyError`, `RequestException` (R@10 1.0).
  context and code_query → `rewind_body`, then `test_rewind_body`, `test_rewind_partially_read_body`, `test_rewind_body_no_seek`,
  `test_rewind_body_failed_seek` (R@10 0.5).

- cJSON “cJSON_InitHooks error exception handling” → after the entity come four `cjson_*_should_fail_on_allocation_failure` tests.
- **Proposed ticket:** "context/code_query: when a question carries terms beyond the entity, rank term-matching neighbours
  above test-file callers."

### F10 — A vendored test framework answers generic questions (fixture pollution)

cJSON vendors the Unity test framework: `tests/unity/**` is 127 of the repo's 229 files. In cJSON's adversarial answers,
51 of 80 search results and 69 of 120 context results come from `tests/unity/**`.
- “utility helper functions” [code_query, ok] → `RakefileHelpers` tests/unity/extras/fixture/rakefile_helper.rb:13
- “what does the function do and where is it called from” [search, context] → `FindFunction_WhichIsBroken` tests/unity/examples/example_1/src/ProductionCode.c:11 (and the example_2/example_3 copies)
- **Proposed ticket:** "Detect vendored and third-party trees (`tests/unity`, `third_party/`, `vendor/`) at index time, and down-weight
  them or expose an exclude control". This is the ticket's acceptance item 4, "generated/test-file and stopword controls".

### Measurement caveats

- Callers labels are matched by name, which is the granularity of the LSP QA sets, so a same-named non-caller counts as a hit.
- P@k for single-target definition questions is bounded by targets ÷ k. Read MRR and entity-first for those.
- The error_handling and adversarial labels are one reviewer's reading of the code, with every item citing file:line.
  The "grounded" outcome depends on the acceptable error-machinery lists, which are deliberately generous.
- Search callers recall (0.089) is low by design: search is lexical, not a graph walk. It is reported, not a defect.
- Chromium (the ticket's large-repository corpus) is not in this gate. See README.md.
